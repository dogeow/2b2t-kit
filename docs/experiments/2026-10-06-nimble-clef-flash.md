# Nimble 与 Clef Flash 的 Minecraft Kit 实验

用户于 2026-10-06 明确要求两个模型均做实验。当前状态：原 Nimble 下载继续，
Clef Flash 下载已启动，自动离线对比程序正在等待模型安装，尚无实测结论。
Ollama 0.35.1；网络优先直连，启动检查确认 32 条 Ollama 连接全部使用 DIRECT。

实验目录：`work/live-20261004/decision-model-pair-001/`。
共同数据集为 `cases.json`：20 个历史及构造的 Kit 状态，每个模型测试两轮。
第二轮反转选项顺序，以检查排序敏感性。两个模型依次加载，沿用服务器
`OLLAMA_MAX_LOADED_MODELS=1`，不同时运行两个推理实例。

案例覆盖健康退出锁、手动接管、未知回执、原木 77/78 数量不符、防护缺失、
安全高空停留、固定树催熟与砍伐、旁侧站位、树根格重叠及正上方站位、
当前地图证据是否充分。正确答案人工固定；这些小样本不能证明无人值守安全。

使用相同 `/v1/systemone` 请求与答案校验，记录决策正确率、首次未加载模型
请求的延迟、后续中位延迟与 P95、Ollama 进程 RSS 采样峰值，以及 API 报告
的模型/GPU 分配。首次延迟包含模型加载，不代表操作系统文件缓存也为冷态。
RSS 与 API 分配数值也不等于完整 Metal 物理内存占用。

Clef Flash 另外使用用户此前提供的两个历史截图，区分 Minecraft 断开连接界面
和自动化进度日志。这是视觉能力补充测试，不直接计入两个模型的 JSON 对比。
它不能证明树冠导航或当前场景操作能力。

模型下载由 `pull-clef.py`（Clef）及原 Nimble 下载进程执行，保留原下载回执。
`compare.py` 等待安装成功后自动测试。一个模型失败会保存原因并继续测试另一个，
不自动替换模型或重放下载。下载或推理未完成时不能填写成功结果。
下载中断时须检查原进程及实际错误；只有直连证实失败后才允许尝试代理。

输出包括 `nimble-results.json`、`clef-flash-results.json`、各模型摘要、
`clef-flash-vision-results.json`、`comparison-summary.json` 和实时进度文件。

目前没有向游戏发送任何动作，没有解除健康锁。实机实验仍待本次健康恢复授权。
恢复后，须先安装已准备的旁侧站位修复，核对新世界、库存、防护及手动接管，
确认旧动作控制器停止后，再由一个 Kit 控制器执行经验证的受限动作，比较两个
模型的选择及对应原生动作结果。离线决策正确不能直接计作实机操作成功。

## 中断与恢复

用户先明确要求停止下载，两个下载客户端及等待对比程序均已正常终止，未执行
删除下载缓存的操作。随后用户要求继续下载并操作 Minecraft，已恢复 Ollama 服务、
两个下载与对比等待程序。旧的用户中断记录保存在实验目录
`prior-user-stop-001/`，不作为本次恢复的网络错误。

恢复时观察到 Ollama 当前进度重新从低值累计，分片元数据的 `Completed` 为零，
不能把此前显示的 22.6%/10.2% 直接算作已恢复的缓存进度。现有分片文件保持原位，
没有手工修改元数据或跳过模型完整性校验。下载连接重新核验为 DIRECT。

本次恢复后，实际日志出现 4 次权重分片停滞重试，直连持续进度很弱。依据用户
“直连不行再走 proxy”的授权，仅将 `PROCESS-NAME,ollama,DIRECT` 改为现有
`PROXY` 组，保留其它规则及代理组选择。关闭原 32 条 Ollama 直连连接，使原下载
请求重新建立连接；没有重启两个下载客户端。后续核验 32 条连接均经过 PROXY，
进度继续增长且未报错。配置备份及证明保存在实验目录 `proxy-fallback-001/`。

确认游戏进程已停止后，已安装旁侧站位修复及对应工作包，游戏未启动，健康锁
文件未改变。实际模型选择、游戏动作与新版本实机验证仍未发生。

## 原生续传失败后的数据恢复

随后两个原生下载均达到重试上限并因 `unexpected EOF` 退出，模型没有注册。
磁盘上的两个部分文件仍实际分配约 7.163 GB 和 7.198 GB，合计 14.36 GB；
原生分片 JSON 只登记约 0.77 GB 续传检查点。累计网络接收量与登记进度、
文件分配空间及完整模型校验是不同证据，不能把其中任何一项当成模型已经完成。

用户确认其手动 `ollama pull` 已关闭后，已启动实验目录中的
`recover-downloads.py`：8 MiB 分块、4 个并发请求，严格核对 HTTP Range、
长度及编码，持久保存各完整小块的本地校验。原生部分文件只读；优先复用
原生检查点以及排除边缘后的已分配文件范围，后者仅作为候选数据。
完整 blob 必须匹配官方 manifest 的 SHA-256 才能加入 Ollama 缓存；候选数据
导致整体验证失败时会重新下载候选范围，不能补写成功。之后仍通过原生
`/api/pull` 注册，并检查安装标签。范围、错误检查点、错误摘要拒绝、正确摘要
及候选数据失败后重取的 5 项回归测试通过。

用户随后要求使用 `clash-p` 切到 PROXY。已查明该别名在 `.zshrc` 中导出
本机 7897 HTTP/HTTPS 代理。小块恢复客户端虽接入了该端口，实际后续路由
此前仍有 SMART-ROUTE/DIRECT。因此仅将 Ollama 实际存储域名和 registry 域名
置于明确的 PROXY 规则，通过 `clash-p` 恢复原检查点；其它规则与组选择不变。
核验 4 条存储连接均经过 PROXY，切换后约一分钟新增 126 MB 有效 HTTP 分块。
该时刻 Nimble 主权重组装约 76.0%，完整模型摘要仍未验证，尚未注册。
网络规则备份和实际连接证明位于实验目录 `clash-p-proxy-001/`。
