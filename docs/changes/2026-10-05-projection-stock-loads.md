# 按缺口一次备料，再逐栈施工

此前把一手材料的施工预算也当作补给预算，导致可用物资足够时仍频繁返回仓库。新纯规划器 `projection_stock_plan.plan_stock` 从当前 43 槽、实际材料缺口、原生堆叠上限及完整元数据计算整载采购量；施工仍按实际手持栈分批，不把它改成更大的盲目打印范围。

- 缺 218 格、空主槽足够、每栈实际上限 64：一次备 226 块，分配为 64、64、64、34；各栈留 2 块，可施工 62、62、62、32，共 218。
- 现有 14+2、还缺 44：补 32 到原 2 块栈，成为 14+34，两栈可施工 12+32。
- 主槽只能装两栈时，如实返回可施工 124 和剩余 94；不声称已备齐。

主槽 0..35 之外、游标和潜影盒内物资不计为可施工现货；不同完整元数据的同 ID 栈受到保护。元数据比较保留嵌套布尔、整数与浮点类型区别，未知容量／元数据时不估算 64。计划区分全部同 ID 总量与实际匹配元数据的可用量，不能把不同元数据目标直接交给旧的 item-only transfer。来源数量和路线仍须现场证明，计划不授权交互或增加放置信用。

实际调用已用于当前砂岩剩余 32 的取料参数：当前只有主槽 5=2、26=2，完整原生审计的缺口为 32，规划输出取 32、目标总量 36、仅主槽 26→34。该输出生成了 `map-take-exact32-cf83.py` 的 `--needed` 参数，取料程序实际确认源箱减少 32、背包增加 32、原生高空守护收尾成功，工人自然退出 0。原件为 `work/live-20261004/map-sandstone-exact32-take-cf83-002/`，规划为 `work/live-20261005-map-goal/bulk-sandstone-current-plan.json`。

新增 14 项纯回归通过独立复核，统一 Python 离线检查共 1514 项通过。后续各材料调用该规划后，必须让已有正常选择／换栈原语逐栈取得实际证据，并将每次施工量裁为实际栈可用量、计划剩余额度和原生窗口上限的最小值。实际有不同元数据物资时需要受限分配执行器，不能只放大最大施工数量。当前实机证据只覆盖砂岩这次取 32；没有宣称其他材料已经全部备好或地图完成。
