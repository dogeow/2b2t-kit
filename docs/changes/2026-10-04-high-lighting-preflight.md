# 高空先核对是否有可执行补光点

region_index 64 的实际暗点虽然存在，冻结规则却没有合法外部火把候选。旧工作流程先下降到地表附近再扫描，因而会进入敌对实体附近，等待 PvE 防护后仍然没有放置工作。

`NativeBatch` 现在完成原有真实短腿预加载和中心完整身体柱核验后，先保持 `max(当前高度, 实际地形顶+24)` 的高空站位。使用同一受保护 `RegionClient` 在高空读取原完整分区，再运行冻结规划器。

只有原生 `DONE`、完整格数、同身份／世界／控制版本和明确空闲防护都通过，才接受零候选。零候选记真实暗点数与 `single_high_preflight_scan`，放置数为 0；不下降、不选择放置物品、不交互，不把一次扫描包装成独立 before／after 两次验证。最终仍须同 owner 原生高空停靠／finish 证明，才推进原工作队列。未知、未加载、部分、身份变化或 guard busy 均保留原请求与 pending，不解释为零，也不自动下降求证。

高空扫描前另外读取当前实际身体完整柱并通过现有 `material_job_park` 元数据接口核对同 owner 的高空 canonical anchor。此接口不启动移动；本地 `park_target` 只在真实原生回执确认后采用。这避免未知 scan 的只读等待把已在高空的玩家错误地比较为旧低处停车。高空 preflight 失败时不调用额外 park／移动／扫描清理；原 request ID、回执及未知账本继续保留。

候选非空时沿用原低处路线、再次实际扫描、逐格交互和两帧／库存守恒验证。高空预测不直接选择低处交互目标，也不增加放置信用。最终完整 ALL150 实际审计和 `goal_complete=false` 范围保持不变；本次只改 Python worker，无新增宿主接口。
