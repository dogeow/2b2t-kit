# 海岛补光实测经验与可复用入口

实际运行使用 `kit_cli.py lighting`，不调用模型、截图或逐格键鼠。显式 profile 定义服务器、维度、分区、授权走位框和建筑/地图画保护范围，原生请求和结果保留在固定 journal。

## 已接入的恢复规则

- 防护会改变角色位置。防护结束后重新核验并回到放置站位，重扫支持块、实体、光照和库存，再写入意图并点击。
- 放置分区与走位范围分开：角色可在明确授权的大走位框内恢复站位，火把仍只能落在原分区。
- 只有明确的原生防护忙碌预派发拒绝才等待稳定后重试。未知交互不重复；低血量、手动输入、世界和控制权变化优先。
- 满血防护忙不能让 Python 停止心跳后误触离线。收尾保持原控制器存活，等待原生防护和原动作终止，再验证停靠。
- 已验证高空停靠仅缺 Flight 时，宿主检查原租约、世界、版本、身体、地形和生命，尝试恢复 Flight 后重新验证真实停靠条件。危险条件仍走既有安全退出。
- 补光旅行扫描的走廊余量为 2.32 格，障碍顶部余量为 5.1 格，防止紧贴星舰顶部的规划忽略相邻障碍。其它材料旅行保留原默认余量；每次实际扫描仍限制 50,000 格。

## 已取消旅行的调和

`lighting reconcile-travel --profile PATH` 只处理记录为 travel 的原批次：原日志只含会话、快照、扫描和导航；有明确空气路线 waiting；当前同世界存在后来的手动停止、无活动租约或导航。原请求、日志哈希和 pending 全部归档，不标为施工完成。随后 `lighting resume` 从实际位置创建新路线。

未知放置、含交互/挖掘的批次、不同世界、仍活动的租约、没有明确停止的请求都不能通过此入口清除。

## 完成证据

火把放置要求两帧实际目标方块与背包精确减少。队列末尾单独扫描每个登记区域，记录剩余暗点和覆盖范围。处理完队列不是整岛完成；保护区、建筑内、树冠下、洞穴和未扫描区域必须分别判断。地图画仍需要完整方块和最终地图像素审计。

本次宿主为 `2026.10.2.1`，引擎为 `1.7.80`。人为在空中关闭 Flight 的实测被自动审批拒绝，未执行；恢复逻辑的隔离测试和宿主接线测试不能代替该场景的实机证明。

## 无 AI 的材料补充入口

火把不足时，分区任务停在 `waiting_materials` 且保持原日志。通过同一个 Kit 的材料接口补充后继续：

```sh
python -B kit_cli.py materials start --item minecraft:torch --count 128
python -B kit_cli.py materials status --job-id 返回的任务编号
python -B kit_cli.py lighting resume --profile 原来的配置文件
```

数量是背包目标数量。材料任务复用已安装版本的配方、工作台、熔炉、燃料和已授权资源配置；材料任务完成并确认背包数量及安全停靠后，再恢复补光。不能在材料任务还持有控制权时启动第二个游戏控制器。
