# 材料任务复用原生自动种田

材料补料原先调用 Python 收获工序，每次最多四株，重复抬升、接近麦田、扫描和原位补种。新增 `planter_wheat_batch` 入口，让同一个材料控制器委托 Kit 已有 `AutoPlanter` 连续收获、拾取和补种，一次指定 1–16 株已登记成熟小麦。

- 原生循环只处理显式原耕地坐标；种田模块保留原来的瞄准、实体遮挡判断、正常破坏及播种交互，不翻耕或扩大田块。
- 每株最多一次破坏启动和一次播种。必须收到当前连接的空气及小麦方块更新，再核对实际背包粮食数量和四粒种子保留量；UI 计数不能成为完成证据。
- 材料访问先保存整批待确认记录；未知结果保留原记录并阻止重放。结束或取消停止本批种田并释放按键，既有手动种田设置不改写。
- 旧宿主继续使用旧工序，新宿主自动使用原生接口。完成后仅做两次整批田块与背包复核，避免每株单独高空往返。
- 地图局部检查识别图面外、实心无液体支撑上的普通可穿过火把；该火把不产生图面完成数量，也不能放宽图面内部块一致性检查。

验证：Java 项目 `test jar verifyRuntimeEngineJar --offline` 通过；Python 原生回执、未知结果不重放、既有麦田及地图火把回归通过。主包版本 2026.10.11.3，需要完整重启一次。实机四株测试通过：背包小麦 0→4，四株均收到收获及补种服务器回执，完成后的两次整片麦田及背包扫描一致。原生批次本身约 8 秒；不把单次样本当作整体提速倍数。证据 `work/live-20261004/native-planter-live-115/wheat/field-00/native-wheat-batch.json`。

实测同时发现耕地顶面 Y+15/16 被既有起飞检查当成上方障碍，导致满血等待收尾。已按真实耕地碰撞高度修复 `_below_vertical_start`，保留当前无液体、无容器和正常净空扫描检查；回归包含高度不足、湿格和未知形状拒绝。原生四株回执保持原字节，原控制器经同会话暂停接口结束，防护保留，没有再次收获或补种。

麦田水格会跨入角色脚边的身体列：原生收麦完成后增加一次最多 1.5 格、只走到已扫描原耕地中央的平走归位，再执行既有起飞检查。移动不收获、不补种、不跳跃；背包必须守恒，未知移动结果保留记录。
