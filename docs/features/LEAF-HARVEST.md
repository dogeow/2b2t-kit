# Kit 自动采集树叶

入口：`decision-runtime/material_jobs/leaf_harvest.py`。`continuous_batch_v2` 复用一个 Kit 原生材料控制器，脚本串联扫描、剪叶和拾取，不调用模型。更新脚本后重开该任务即可，不替换 Mod 主包、不重启 Minecraft；目前没有独立 GUI 按钮。

从引擎 **1.8.61** 起，推荐配置 `execution: native_burst`、`batch_size: 16`。连续剪切在游戏线程内完成，Python 只下发整批目标、走位和结算。每片使用正常 Minecraft 破坏接口；悬空时持续剪几帧，看到本地破坏后就转向下一片，整批结束后统一等待 Vanilla 预测校正退休，核对真实加载区块的残留叶块。只有校正已结束且仍存在的天然叶子才允许下一批补剪，每处最多两批；未知批次身份保留且不重发。`serial` 模式保留旧的逐格确认流程。

2026-11-08 实机验收：背包橡树叶 **217 → 247**，30片新增全部实际入包，总计 **42.55秒**（含热加载、区域扫描、一次接近及拾取），约 **42.3片/分钟**。本轮37格确认移除，尚未观察到拾取的7片未计入成绩；结束时没有 pending，角色满血、满饱食，保留在线 PvE 防护。该成绩是本轮现场记录，不代表所有地形的固定速率。

## 准备与启动

在 `2b2t-kit` 目录，使用已安装 decision-runtime 依赖的 Python。先复制 `decision-runtime/examples/leaf-harvest.json`，替换源区域、保护范围、安全高空停靠点及专用树叶存放箱坐标。示例中的 0 坐标只是占位，不是当前基地。

`server` 必须与 Kit 实际连接的地址一致（例如 `127.0.0.1:25566`），不把代理地址自动视为其他世界。源区域是明确允许剪叶的范围；一块区域每轴最多 32 格、体积最多 50000 格，支持多个区域。脚本只采非含水且 `persistent=false` 的天然树叶，保护人工树叶、容器和保护区域。箱子必须明确指定，不能把附近任意交易中心箱子当作专用存放箱。

先做离线配置校验（没有游戏动作）：

```bash
PYTHONPATH=decision-runtime python3 -m material_jobs.leaf_harvest \
  --config /path/to/leaf-job.json --out /path/to/leaf-job-state
```

实际启动：

```bash
PYTHONPATH=decision-runtime python3 -m material_jobs.leaf_harvest \
  --config /path/to/leaf-job.json --out /path/to/leaf-job-state --run
```

默认 `target_scope: total_stock`：目标 `4000` 包含启动时背包中已有的树叶，加上本任务新增并确认拾取的叶子（含本任务随后确认存箱的数量），各树叶种类一起累计。其他箱子里未核验的旧库存不计数。若明确需要再采 4000 个，可设置 `target_scope: new_collected`。剪刀放在主背包或快捷栏即可；手中剪刀剩余耐久至少 2 时继续使用，只有不适用时才切换。没有可用剪刀时等待，不自动消耗铁锭制作。

批次参数可省略：`batch_size` 默认 12，原生模式上限32、建议16，串行模式上限16；`pickup_grace_seconds` 默认 0.5、范围 0–3 秒；`approach_seconds` 默认 12、范围 4–30 秒。这些参数分别限制一批连续开采数量、整批拾取前的短暂观察、一次接近的时间。

## 自动流程

- 严格核对当前服务器、世界、生命、食物、防护、人工输入及扫描覆盖。一个任务目录有一个进程锁，不重启或抢占正在运行的控制器。
- 区域扫描后缓存候选，在当前站位优先连续剪同种可达叶子；附近剪完再接近下一处，接近面按角色与目标的相对位置选择。接近前重新观察，叶子已经消失时跳过，天然叶子距离属性变化时使用新状态。每片仍保留一次局部开采前检查，保护人工树叶、相邻液体及容器。
- 一批最多连续开采 12 片，每次请求都写入意图，并验证该格服务器更新、原生序列和 ACK；未知请求立即阻止后续开采。剪刀耐久可用时不反复选择物品，批次内不等待每片自动吸取。
- 批次结束只短暂观察一次，按已确认开采总量核算实际背包增量；现场新掉落可以合并为一堆，复用原生唯一 UUID 拾取。移动中同时吸到本批其他叶堆时，全部增量仍不得超过已确认开采预算。预先存在的掉落不会被当作本批新掉落。
- 未观察到拾取的数量保留为 `outstanding`，不给完成数加分；以后出现的延迟背包增量只能在已确认但未计数的数量以内补计。拾取请求未知、数量越界或原生确认缺失时保留 `pending` 与 `batch`，不重放。
- 空位低于预留数量时，仅把本任务新增的树叶存入指定箱子，保留任务开始时的原有树叶及全部装备、工具、食物、图腾、末影箱和潜影盒。复用现有容量检查和存取回执。箱满或未配置箱子时等待。
- 只根据已确认拾取增量更新完成数；最终核对背包与任务已确认存放量的守恒关系。授权区域无可达叶片时等待补充源区域，不擅自外出无限搜索。

## 状态、停止与续跑

```bash
PYTHONPATH=decision-runtime python3 -m material_jobs.leaf_harvest \
  --out /path/to/leaf-job-state --status

touch /path/to/leaf-job-state/STOP
```

`STOP` 在下一安全检查点停止；不会取消已经发出的未知开采。GUI、人工接管、生命保护始终优先。正常结束释放本任务的控制权并保留 PvE 防护，不在每片后飞高，也不主动重登。

进度保存在 `leaf-progress.json`；原生回执在 `control/` 中。续跑使用同一 `--out`。只有原世界、配置和背包仍一致、没有 `pending` 或未结算 `batch` 时才可继续；重新登录、人工改动物资或待确认操作均要求先核对原凭证。`metrics` 记录原生开采数、批次数、换剪刀次数和接近次数，便于对照效率。

原生模式的整批意图与结果在 `native-bursts/`；游戏端消费凭据在 `leaf-shear-claims/`。同一批次 ID 即使热加载或重连也不再次执行。主任务必须持续持有同一个材料租约；游戏端逐帧检查人工输入、原世界、修订、手持剪刀、生命、食物与方块类型，不能借连续剪叶扩展到原木、容器或其他方块。可用 `--wait-idle-seconds 60` 先只读等待3秒稳定空闲再取得控制。

这次热更新通过 `tools/build_leaf_shear_overlay.py` 在已安装1.8.58的固定哈希基线上构建，只添加剪叶类、一个 guard tick 调用及版本号；保留基线的其它类，避免把工作树中其它引擎改动一起部署。已做依赖闭包与 JVM 字节码校验，产物差异清单随构建保存。正常源码构建通过 `DefaultTunnelBorerEngine.tickStandaloneGuard` 中同一个调用接入。

若原任务已停止，且最后一次拾取有匹配原 UUID、物品、数量和世界的明确终止回执，可以加 `--resume-batch` 先结算原批次。它保留旧回执、跳过已经尝试的旧 UUID，只按已确认数量核对合并后的新叶堆；原批次结算前不会再剪叶。存在未知请求文件、原开采未确认或世界变化时拒绝该入口。已知的叶堆合并／消失终止回执不会重复发送旧拾取；新 UUID 是一次新的、受整批数量约束的拾取。

收尾先确认最后一个原生请求已结束，再发送一次原生暂停并释放本任务租约、保留 PvE 防护，最后关闭心跳。原生结果未知时只观察并维持原心跳；应用层仍有未拾取记录，并不等同于有未知的原生操作。该顺序避免先关心跳触发宿主的退出兜底。

## 验证边界

离线回归覆盖连续批次的调用次数、统一拾取与合并掉落、延迟增量上限、服务器确认、自然消失、人工暂停、保护区、剪刀切换、背包容量和存箱失败。2026-11-08 旧流程实测 33 片约 319 秒，含 34 次换物、55 次扫描；这是优化前的参考，实际提速以新流程原生回执与背包增量为准。通过测试不代表 4000 片已采齐。
