# 只开 Minecraft 的调用方式

当前入口是 HMCL 的 **26.1.2** 实例，已实机加载 Kit **2026.10.6.2**。

进入服务器后，按 **U → 生产**：

- **自动砍树**：原生砍伐、拾取和补种。
- **材料任务**：选择物品及背包目标数量，点击“开始获取材料”。
- **投影建造**：使用已经加载并正确放置的 Litematica 投影。
- 投影材料模式提供“自动补齐并建造”；它仍依赖已登记的真实物资来源与实际支持的采集能力，不能保证任意材料都能自动获得。

这些入口不需要打开 ChatGPT 或 Ollama 桌面界面。原生游戏功能直接在 Minecraft
内执行；材料流水线可能由 Kit 启动一个轻量的后台 Python 工作进程，不需要
另开终端窗口。缺少来源或能力时会报告具体缺口。

## 两个本地模型目前的状态

Nimble 和 Clef Flash 已完整下载并通过官方 blob 摘要校验、原生 Ollama 注册。
目前仅做了离线决策回放，**尚未接入游戏菜单，没有模型实机操作验收**。
不要把 `ollama run` 当作 Minecraft 控制入口；模型本身也不具备游戏接口。

18 GiB 的这台机器上，本次 Nimble 的模型分配约 8.87 GB；Clef Flash 约
13.07 GB。此前同时运行游戏、ChatGPT 和大模型时，系统交换内存达到约 9.3 GB。
关闭模型 GUI 并不等于卸载模型权重。

为避免常驻负担，目前两个模型均已卸载，实验和下载进程已结束，实验专用
Ollama 服务已停止，文件保留。默认继续使用 Kit 的原生入口。
如果以后接入本地 AI，需要实现游戏内的可选入口、限制上下文、按需启动服务
并在调用结束后卸载；单靠这些措施也不能保证默认 9B 模型与游戏同时运行不卡。
不能将这个尚未实现的接入方案当成当前功能。

实验结果已保留：Nimble 40 次判定中 28 次符合预设标签；Clef Flash 仅完成
10 次，其中 6 次符合标签，后因内存压力暂停。两者的测试范围和完成度不同，
不能据此宣布哪个更适合控制游戏。
