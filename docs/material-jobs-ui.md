# 材料任务入口与直接 API

## 无需界面的控制方式

后续自动化通过已安装后台目录中的 `kit_cli.py` 直接调用 Kit，不需要截图、按键或打开游戏菜单：

```text
python kit_cli.py materials start --projection
python kit_cli.py materials start --item minecraft:white_concrete --count 64
python kit_cli.py materials status
python kit_cli.py materials pause --job-id material-job-...
python kit_cli.py materials resume --job-id material-job-...
python kit_cli.py materials cancel --job-id material-job-...
```

`python` 使用已安装的材料后台虚拟环境。其它游戏目录可在 `materials` 前传 `--game-dir <版本目录>`。投影启动直接读取当前最新选定投影；暂停、继续、取消必须明确指定任务编号，防止控制另一个任务。

结果是紧凑 JSON。`phase: done` / `accepted: true` 只表示宿主接受这次 API 请求；实际进度以 `material_task.state`、`done`、`total` 和 `process_alive` 为准，不代表施工已经完成。

Python 也可直接使用 `material_task_client.MaterialTaskClient(automation_root)` 的 `start_projection()`、`start_item(item,count)`、`status(job_id=None)`、`pause(job_id)`、`resume(job_id)`、`cancel(job_id)`。

控制使用独立的 `material-task-request.json` 与 `material-task-reply-<请求编号>.json`，不会覆盖材料施工正在使用的 `request.json`。文件锁与原子写入防止并发覆盖；已有未消费请求或等待回执超时时会明确报错，不自动重发。启动和继续核对最新世界、控制版本及安全锁；停止任务不会解除安全锁。旧主包会提示更新，不以 UI 操作回退。

## 游戏内使用

- 打开 Kit → **生产 → 材料任务**，选择物品，输入希望背包最终持有的数量，再点 **开始获取材料**。
- 物品选择支持当前游戏语言名称和完整 ID；已有物品计入目标数量。列表列出当前游戏原版物品，实际是否能够自动取得由本地材料后台返回能力和缺口。列表中可选择不代表已经实现该物品的采集能力；缺少能力、工具或可达材料来源时，任务明确停止并说明原因。
- 打开 **投影建造 → 自动补齐材料并建造**，使用当前选定且锁定的投影。后台核对缺料后执行取料、采集、制作与施工。
- 投影补料优先消化实际箱内现货：一次补料阶段会在批准仓库中顺便取可施工的其它成品，保留一个周转空格；背包确认新增后先施工一次，再继续缺料链。不会把旧仓库记录当作到手物品。同一差料状态不重复全库扫描。
- 制作前也会先取已有中间成品，再重新计算原料。例如高炉需要的普通熔炉、铁锭和平滑石已有库存时，优先取用，减少重复挖矿和熔炼。
- 任务运行时可返回材料页查看状态、暂停、继续或取消。暂停先安全收尾，只有点击继续才恢复；取消保留已取得的材料。
- 首页只显示用户收藏的功能。材料任务不会自动加入首页。
- 作业信息使用现有顶部 HUD，显示物品、实际进度和阶段，复用目标方块信息避让；怪物防护和恢复生命状态优先显示。

## 本地后台和交付

默认后台入口是游戏配置目录中的 `twob2tkit/material-worker/material_jobs_cli.py`，整个后台目录需随版本部署。Python 优先使用明确配置的路径，然后读取安装器写在后台目录的 `runtime-python.txt`，最后才从环境 `HOME` 或 Java 用户目录查找。这样 HMCL 将 Java 用户目录隔离到 `/Applications` 时也能使用真实用户的运行环境。

配置字段 `materialJobsWorker`、`materialJobsPython` 可覆盖上述安装路径；它们是 JSON 配置字段，目前没有独立的高级设置界面。常规游戏流程不需要填写实现路径。启动使用独立参数列表，不调用 shell，不传入模型凭据。

任务记录位于 `config/twob2tkit/automation/material-jobs/<任务编号>/`：

- `request.json`：任务种类、目标数量、当前注册表全部物品的实际堆叠上限、投影标识及世界/控制版本。堆叠上限只在启动请求写一次，不增加每帧游戏快照。
- `status.json`：后台确认的状态、阶段、原因与数量；不同编号或无效回执不会更新当前进度。
- `control.json`：用户明确的暂停、继续或取消操作。继续时附当前世界和控制版本，后台重新取得租约，不复用旧版本绕过控制检查。
- `worker.log`：后台输出。界面可复制任务记录目录。

宿主只负责启动、任务界面和生命周期。本地后台负责确定性计划、材料与游戏动作；正常执行不需要 AI。

## 已接入的材料链

仓库取料包含登记的材料箱及配置的末影箱／潜影盒。临时潜影盒沿用取出、放置、取料、回收、放回的对账流程；未确认回收时不会继续下一盒。配方来自当前 Minecraft 版本文件，支持普通工作台配方和普通熔炉配方，16 种混凝土包含粉末合成与遇水固化。

直接采集适配包括沙子、沙砾、九种主世界原木、圆石、深板岩圆石、铁／铜原矿、煤和安山岩等常见自然岩块。资源搜索保存已访问区域，避开已登记基地、投影、容器、液体与不安全入口。地下岩区采用逐段核验的竖井，离开时回到实际通透入口，不在地层里直线飞行。

投影补料会优先取箱子里能够立即施工的成品，并用实际背包增量确认后再施工；不会只盯住一种缺料而忽略其它现货。同一份差料清单只额外检查一轮批准仓库。制作前也会查询配方中的现成中间材料（例如铁锭、普通熔炉、平滑石），然后按取到的数量重新计算采集缺口。

自动取料和制作可以组合成多级配方；这不代表已实现所有物品的原料采集。羊毛、特殊染料、稀有掉落等若库存不足且没有采集适配，会显示具体缺项。工具、食物、背包空间、仓库容量或工位条件不足也会明确停止，不能把“可选择这个物品”解释为保证能从任意环境取得它。

工位按服务器和维度保存在 `config/twob2tkit/material-profiles/`，资源搜索记录在 `material-resource-ledger/`。当前 Simpcraft 基地的既有工作台、六个熔炉、材料箱和固化工位已经迁入配置；每次操作仍会重新核验方块。换世界不会沿用另一世界的坐标或未完成加工账本。

## 维护者打包与更新

在 `decision-runtime` 中使用已有 Python 环境执行：

```text
python material_worker_release.py --out ../build/material-worker.zip --check-imports
```

这一步只生成源码 ZIP 并在临时目录验证实际 CLI/backend 导入，不安装、不启动游戏或联网。压缩包包含逐文件校验清单；排除测试、密钥、配置、运行缓存和玩家数据。相同源码生成相同内容哈希。

更新已安装后台时，显式追加 `--install-game <游戏版本目录>`。安装前拒绝正在运行的材料后台，自动保存旧目录并在目录切换失败时回滚。启动器和游戏均不会被该脚本打开。Python 环境需已有依赖；目前共用客户端组件仍依赖 `httpx`，即使正常材料任务没有模型调用。脚本不会自动联网安装依赖。

安装器使用 `--python` 指定的可执行文件（默认当前 Python）写入本机 `runtime-python.txt`，保留虚拟环境路径，不解析掉其符号链接。这个本机记录不进入源码 ZIP，也不参与导入校验。即使源码没有变化，改用另一个 Python 安装时仍会更新路径并备份旧记录。

## 生命周期约束

启动前检查运行环境、当前世界和控制权，关闭界面后再次核对。后台不存在时直接显示错误。每次新任务使用新的编号与目录，不从旧文件自动恢复控制。

低血量锁不会由启动器解除。急停、离开世界或退出游戏会结束自有后台；跨世界不会悄悄继续。停止使用确切进程句柄，不按进程名称批量关闭其它程序；旧后台尚未退出时不能启动第二个后台。后台报告完成后还需正常退出，界面才显示已完成。后台退出时若留下缺能力等原因，界面保留该原因。

暂停续接只在原世界里发生。已确认停稳、无光标/合成格物品、无未收回临时资源的步骤可以按当前背包重新规划。结果不明的物品操作和未确认在制品保留检查点，不能因点击继续而重复投料。

地下采坑结束后，材料后台先读取本次世界里已核验的入口记录，再重新扫描脚部、头部和整条竖井。角色会沿已挖空的空间回到入口中心，再垂直升到地表上方；不会为了返程挖新通道或直接穿过顶层石头。入口积水、被堵、扫描未确认或实际走位不符时停止。这个能力要求宿主支持精确的仅空气导航，旧宿主会明确提示更新。

UI、宿主生命周期与配置入口需要完整重启才能生效。离线测试覆盖任务协议、状态/退出结果、栏目归属和 HUD 优先级；它们不代替实际服务器采集和施工验证。
